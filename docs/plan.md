  - 폴더·계정을 바꾸면 선택을 해제한다

  - 통합 받은편지함에서도 동작한다 (메일이 속한 계정의 휴지통으로 이동)
  - 테스트: 선택·해제·범위 선택, 선택 0건일 때 삭제 버튼 비활성, 삭제 호출 횟수와 확인 취소 시 호출 안 됨

## M7. 검색·알림·마무리

- [x] 계정 내 검색(FTS5), 통합 받은편지함 실데이터 연결
  - 제목 표시줄 검색창에 입력하면 0.3초 뒤 검색한다. 계정을 골랐으면 그 계정, 통합 보기면 모든 계정의 모든 폴더에서 제목·보낸사람·본문을 접두 검색한다. Esc로 지우면 원래 목록으로 돌아간다

  - 검색 결과에서 삭제하면 휴지통 여부를 알 수 없어 항상 확인 창을 띄운다. 폴더·날짜·읽음 같은 검색 필터는 아직 없다
- [x] Windows 알림, 트레이, 시작 시 실행

  - 시작 프로그램으로 켜지면(`--minimized`) 창 없이 트레이로 시작한다
  - 남은 것: 계정별 알림 켜기/끄기와 알림의 보관·읽음 버튼은 설정 화면 작업에서 한다. 실제 알림·트레이는 `pnpm tauri dev`로 눈으로 확인하지 않았다
- [x] 키보드 단축키, 설정 화면

  - 설정 화면(제목 표시줄·레일의 설정 버튼, Esc로 닫기): 일반(Windows 시작 시 실행, `get_autostart`/`set_autostart`), 계정(계정별 서명 편집), 모양(라이트·다크·시스템, localStorage 저장), 단축키(목록)

- [x] 설치 파일 빌드(NSIS), 자동 업데이트
  - `.github/workflows/build.yml`: main에 푸시할 때마다 검사(프론트·Rust) 후 `pnpm tauri build`로 NSIS 설치 파일을 만들어 아티팩트로 올린다
  - `.github/workflows/release.yml`: `v0.2.0` 같은 태그를 푸시하면 설치 파일·서명·`latest.json`을 GitHub 릴리즈로 올린다. 태그와 `tauri.conf.json` 버전이 다르면 실패한다
  - 앱(`src-tauri/src/updater.rs`): 시작 30초 뒤와 6시간마다 `releases/latest/download/latest.json`을 확인해 새 버전이면 받아서 설치한다(passive 설치, 설치 뒤 앱 재시작). `tauri dev`(debug)에서는 자동 확인을 하지 않는다
  - 설정 > 일반 > 업데이트: 현재 버전, "업데이트 확인", "지금 업데이트"(진행률 표시)

  - 남은 것: 실제 릴리즈로 업데이트 흐름을 눈으로 확인하지 않았다(첫 릴리즈는 `v0.1.0`, 그다음 `v0.1.1`을 올려 0.1.0 앱이 업데이트되는지 확인). 코드 서명이 없어 설치 때 Windows SmartScreen 경고가 뜰 수 있다

  - 앱 아이콘 원본이 확정되지 않았다면(사전 준비의 Claude Design 결과물) 그것부터 정한다

- [x] 계정 추가 마법사 완성 — 디자인(S-03, `docs/design/AddAccount.dc.html`)의 ③④ 단계가 빠져 있다 (ACC-01)
  - 완료 메모: ①②는 한 화면(서비스 라디오+입력), ③ 이름·색(`add_account`에 `color_index` 추가), ④ 진행 팝업(남은 수만 표시, 계정 전체 합계, 이벤트 사전 구독). 폴더별 행·남은 시간 추정·비밀번호 표시 토글은 뺐다. `pnpm tauri dev`로 눈으로 확인 못 함.
  - 현재(`features/accounts/AddAccountDialog.tsx`)는 ①서비스 선택·②아이디/앱 비밀번호 입력까지만 있고, 성공하면 바로 닫힌다
  - ③ 표시 이름·계정 색 선택: 표시 이름 입력(기본값은 메일 주소 앞부분), 8색 팔레트(`--account-N` 토큰, 이미 쓰는 색은 표시) 중 선택. `add_account`는 이미 `name`을 받지만 UI가 안 보내 메일 주소가 이름이 된다. 색(`color_index`)은 `계정 수 % 8 + 1`로 자동이라 인자로 받도록 확장한다. 추가 뒤 설정에서 이름·색을 바꾸는 것은 별도 작업
  - ④ 전체 메일 동기화 진행 팝업: 받은 메일 수 / 전체 진행률, "창을 닫아도 백그라운드로 계속 받아요" 안내, 닫기 버튼. 진행률은 기존 `sync-progress` 이벤트(`onSyncProgress`)를 쓴다. 지금은 제목 표시줄에 "메일 가져오는 중 n/m"만 나온다(`App.tsx`)

    4. 한꺼번에 여러 통을 지울 때(선택 삭제) 중간 상태로 한 번만 읽어 마지막 값을 놓치는지

    - 메뉴는 키보드(방향키·Enter·Esc)와 스크린리더로 쓸 수 있어야 한다(`role="menu"`, 포커스 이동). 바깥을 누르면 닫힌다. 스타일은 `tokens.css`의 값만 쓴다(팝업 모서리 10px)
  - 실패 처리: 서버에 못 보낸 조작은 큐에 남고 다음 동기화 때 다시 보낸다(기존). 휴지통/보관 폴더를 못 찾으면 한국어 안내를 알림 영역(`notice`)에 띄운다. 모든 동작 뒤 메일 목록·안 읽은 수는 다른 작업과 같은 갱신 경로로 다시 읽는다(삭제 배지 수정 작업과 같이 진행)
  - 테스트: 삭제 버튼이 `deleteMail`을 부르고 휴지통 안이면 확인 창이 먼저 뜸, 삭제·보관 뒤 다음 메일이 열림, 보관은 계정 종류별 대상 폴더로 `moveMail`을 부르고 실행 취소가 원래 폴더로 되돌림, 이미 보관된 메일은 비활성, 더보기 메뉴 각 항목이 해당 호출을 하고 키보드로 열고 닫힘. Rust: `FakeProvider`로 보관 대상 폴더 결정(Gmail은 `\All`, 네이버는 없으면 만들기), 이미 있으면 다시 만들지 않음

## 추가 기능

작업 하나씩 아래에 추가한다. 요구사항 ID(`docs/requirements.md`)가 있으면 함께 적는다. 이미 "남은 것"으로 적어 둔 후보: 메일 보관(e)·계정 표시 이름·색·순서·알림 켜기/끄기·동기화 주기·계정 제거, 작성 창 분리, 서식 편집, 끌어놓기 첨부, 검색 필터, 업데이트 끄기 설정.

- [x] 첨부파일 다운로드 — 받은 메일의 첨부를 저장하는 기능. 지금은 목록만 보이고 저장 버튼에 동작이 없다
  - 완료 메모: 마이그레이션 `0007_attachment_part.sql`, `fetch_attachment`(IMAP `BODY.PEEK[]` 전체를 메모리로 받아 파트 추출), `save_attachment`/`save_all_attachments`/`reveal_saved_attachment`, 저장 대화상자는 Rust(`tauri-plugin-dialog`). 남은 것: 스트리밍·진행률, 설정의 기본 저장 폴더, 열기/미리보기, 전달 시 원본 첨부, 저장 대화상자·탐색기 열기 실앱 확인, 실서버 확인.
  - 현재 상태(코드 확인): 동기화는 첨부의 이름·크기·확장자만 `attachments` 테이블에 저장하고 내용은 받지 않는다(첨부는 열 때 내려받기로 한 결정, 요구사항). `Reader.tsx`의 저장 버튼(`aria-label="… 저장"`)은 `onClick`이 없고, 크기는 `a.size`를 그대로 찍어 숫자로 보이며, 목록 `key`가 `a.name`이라 이름이 같은 첨부가 둘이면 충돌한다. `get_mail`의 첨부 모양에 내려받을 대상을 가리키는 값이 없다
  - 백엔드
    - 첨부가 메일의 몇 번째 파트인지 알아야 한다. 마이그레이션 파일로 `attachments`에 `part_index`(파싱 순서)와 `mime`을 추가하고, 파싱(`providers/imap/parse.rs`)이 채우게 한다. 이미 저장된 메일은 값이 없으므로 내려받을 때 원문을 다시 받아 이름·크기로 맞추는 대비책을 둔다
    - `MailProvider`에 `fetch_attachment(folder_key, remote_id, part)`를 추가한다(기본 구현은 `Unsupported`, `FakeProvider`와 IMAP 구현체에서만 서비스 차이를 처리). IMAP은 `UID FETCH … BODY.PEEK[<파트>]`로 해당 파트만 받는다(전체 메일을 받지 않게 BODYSTRUCTURE로 파트 번호를 찾는 방법을 우선 검토하고, 어려우면 `BODY.PEEK[]` 전체를 받아 파싱한다). `\Seen`이 달리지 않게 반드시 PEEK를 쓴다. Gmail은 같은 메일이 여러 폴더 사본이어도 이 앱에 저장된 폴더 기준으로 받는다
    - command는 `save_attachment(mail_id, attachment_id)`와 `save_all_attachments(mail_id)` 정도로 둔다. 저장 위치는 Rust 쪽에서 Tauri 파일 저장 대화상자(`tauri-plugin-dialog`, 기본 파일 이름 채움)를 열어 정한다. UI는 `invoke`만 부르고 파일 경로를 직접 다루지 않는다(아키텍처 규칙). 대화상자를 취소하면 오류가 아니라 "취소됨"으로 돌려준다. 권한은 capabilities에 필요한 것만 추가한다
    - 받은 데이터는 DB에 영구 저장하지 않는다(용량). 선택 사항으로 방금 받은 첨부는 임시 폴더에 두고 "폴더에서 보기"·"열기"에 쓴다
    - 안전: 파일 이름은 경로 구분자·`..`·제어 문자·Windows 예약 이름(CON, NUL 등)·끝의 점/공백을 정리한 뒤 쓴다. 이름이 겹치면 `(1)`을 붙인다. 실행 파일(`.exe`·`.bat`·`.js` 등)은 저장은 되지만 열기 버튼은 두지 않거나 확인을 받는다. 메일 안 내용은 신뢰하지 않는다. 네트워크 호출에는 타임아웃을 건다(큰 첨부는 진행 이벤트로 알리고 전체 타임아웃은 두지 않되 무응답 타임아웃만 건다)
  - UI(`Reader.tsx`)
    - 첨부 카드: 확장자 배지·이름·사람이 읽는 크기(`1.2 MB`, `format.ts`에 크기 형식 함수 추가)·저장 버튼. 클릭하면 저장 대화상자 → 받는 동안 카드에 진행(스피너 또는 퍼센트), 끝나면 "저장했어요 · 폴더에서 보기", 실패하면 한국어 안내와 "다시 시도". 첨부가 2개 이상이면 "모두 저장"
    - 오프라인이면 받을 수 없다는 안내를 보이고, 이름이 같은 첨부도 `key`에 id를 써서 구분한다. 접근성: 버튼 라벨에 파일 이름·크기를 포함한다
    - 인라인 이미지(`cid:`)는 첨부 목록에 없으므로 이 작업 범위가 아니다. 이미지·PDF 첨부 미리보기는 후속
    - 전달할 때 원본 첨부를 싣지 않는 현재 제한(결정 로그)은 이 작업으로 풀 수 있지만 별도 작업으로 둔다
  - 정할 것: (a) 저장 대화상자를 매번 띄울지, 기본 다운로드 폴더(Windows 다운로드)에 바로 저장하고 "폴더에서 보기"를 줄지(제안: 첫 구현은 대화상자, 설정에서 "항상 이 폴더에 저장"은 후속) (b) 크기가 큰 첨부(수십 MB)의 메모리 사용 — 스트리밍으로 파일에 바로 쓸지
  - 테스트: `FakeProvider`로 첨부 파트를 내려받아 지정 경로에 쓰고 내용이 같음, 위험한 파일 이름이 정리됨, 같은 이름이 있으면 번호가 붙음, 대화상자 취소 시 아무것도 쓰지 않음, `Seen` 플래그가 바뀌지 않음(PEEK), 오프라인 오류가 한국어 안내로 나옴. UI: 저장 버튼이 `saveAttachment`를 호출하고 진행·완료·실패 상태가 보임, 이름이 같은 첨부 둘이 각각 동작함. 실서버(네이버·Gmail) 확인은 사용자가 요청할 때

- [x] 휴지통·스팸함 전체 비우기 — 폴더를 열었을 때 한 번에 모든 메일을 완전 삭제한다
  - 위치: 메일 목록 헤더(또는 폴더가 휴지통·스팸함일 때만 목록 위에 뜨는 안내 줄)에 "휴지통 비우기" / "스팸함 비우기" 버튼. 해당 폴더에서만 보이고, 메일이 0통이면 비활성
  - 확인 창 필수(되돌릴 수 없음): "휴지통의 메일 N통을 완전히 삭제할까요? 되돌릴 수 없어요." 개수는 서버가 아니라 로컬에 있는 수라서 "전체"와 어긋날 수 있으므로 문구를 "이 폴더의 모든 메일"로 한다
  - 백엔드: `empty_folder(account_id, folder_id)` command를 추가한다. 휴지통(`FolderKind::Trash`)·스팸(`Spam`) 종류만 허용하고 다른 폴더는 거절한다(실수로 받은편지함을 비우는 것 방지). 서비스 차이는 `providers/`에서 처리: IMAP은 `\Deleted` 일괄 설정 + `EXPUNGE`, Gmail은 휴지통·스팸에서 `\Deleted`+EXPUNGE가 영구 삭제인지 확인한다
  - 로컬에서 먼저 지우고(낙관적) 서버 조작은 `pending_ops` 큐로 보낸다. 오프라인이면 큐에 남는다. 수천 통도 한 번의 조작으로 처리해 연결을 여러 번 맺지 않는다. 진행 중에는 버튼을 비활성화하고 끝나면 목록·안 읽은 수를 다시 읽는다
  - 통합 보기에서는 폴더 개념이 없으므로 버튼을 두지 않는다(계정을 고르고 그 계정의 휴지통·스팸함에서만)
  - 테스트: 휴지통·스팸함에서만 버튼이 보임, 확인 취소 시 호출 안 됨, 확인하면 `emptyFolder` 호출, 0통이면 비활성. Rust: `FakeProvider`로 휴지통·스팸만 허용하고 다른 폴더는 거절, 비운 뒤 로컬 메일 0통, 오프라인 시 큐에 남음
  - 완료 메모: `empty_folder(account_id, folder_id)` command(휴지통·스팸 종류만 허용, 그 외 `NotEmptiable`로 거절), `OpKind::EmptyFolder`(`pending_ops`에 한 건, 마이그레이션 불필요 — `kind`는 자유 텍스트), `MailProvider::empty_folder`(기본 `Unsupported`, IMAP은 `STORE 1:* +FLAGS \Deleted` + `EXPUNGE`를 한 연결로, 빈 폴더는 건너뜀). UI는 `features/mail/EmptyFolderBar`(확인 창 "이 폴더의 모든 메일", 0통이면 비활성)를 `MailList`의 `topBar` 슬롯에 끼움. 통합 보기·검색 중에는 숨김.
  - 남은 것: 실서버(네이버·Gmail)에서 `EXPUNGE` 영구 삭제 확인, 동기화가 로컬 비우기와 서버 반영 사이에 끼어들 때의 재수신 가능성(`sync_account`는 시작 때 큐를 먼저 보내 대부분 막음), 실창 육안 확인.

## 디자인 불일치 수정

`docs/design/`(특히 `Main.dc.html`)과 구현이 어긋난 곳을 하나씩 맞춘다. 작업 시작 전 디자인 파일의 해당 부분을 열어 크기·간격·토큰을 대조하고, 끝나면 이 목록에서 체크한다. 아래 4건 외에도 눈으로 보다가 발견한 차이는 이 목록에 추가한다.

- [x] 통합 받은편지함의 계정 색 표시 — 디자인은 행 왼쪽 **세로 막대**(폭 3px, 계정 색 `--account-N`)인데 구현(`MailList.tsx`의 `accountDot`)은 이름 옆 **점**이다
  - 점을 없애고 행 왼쪽 가장자리의 세로 막대로 바꾼다. 통합 보기(`showAccount`)에서만 보인다. 색은 `var(--account-${colorIndex})`, 크기는 디자인 값을 `tokens.css` 변수로 쓴다(하드코딩 금지). 안 읽음 점·선택·hover 배경과 겹치지 않는지 본다
  - 계정 이름은 막대의 툴팁/접근성 라벨(`aria-label`)로 남긴다. 테스트: 통합 보기에서만 막대가 있고 계정별 색이 맞음, 개별 계정·폴더 보기에서는 없음
  - 완료 메모: 이름 옆 점을 행 왼쪽 세로 막대(폭 3px, `--mail-row-bar-width`·`--mail-row-bar-inset` 토큰, `--account-N`)로 교체. 계정 이름은 `aria-label`/툴팁

- [x] 라벨 색 적용 — 라벨(Gmail 라벨)의 색이 어디에도 반영되지 않는다
  - 확인할 곳: 폴더 패널의 라벨 목록(`FolderPane.tsx`)의 색 점, 메일 목록 행의 라벨 칩(`MailList.tsx`, 지금 `m.label.colorIndex`를 계정 팔레트로 칠함), 본문 헤더의 라벨. 라벨 색의 출처를 정한다: Gmail은 IMAP으로 라벨 색을 주지 않으므로 앱에서 라벨 이름 기준으로 팔레트에서 안정적으로 배정(해시 → `--account-N` 같은 8색 또는 별도 라벨 색 토큰)하고 저장할지, 사용자가 고르게 할지 정한다(제안: 자동 배정+설정에서 변경은 후속)
  - 같은 라벨은 어느 화면에서나 같은 색이어야 한다. 한곳(`labelColor(label)`)에서 계산해 폴더 패널·목록·본문이 공유한다. 라이트·다크에서 글자 대비를 확인한다
  - 테스트: 같은 라벨 이름이 폴더 패널·목록 칩에서 같은 색 변수를 씀, 다른 라벨은 색이 다를 수 있음, 색 값이 `tokens.css` 변수만 사용
  - 완료 메모: `src/lib/labels.ts`의 `labelColor`(이름 해시 1~8, 백엔드 `label_color`와 같은 계산)를 폴더 패널·목록 칩·본문 헤더가 공유. 폴더 패널은 `labelPaths`로 "부모/자식" 전체 이름을 만들어 해시한다. 사용자 지정 색은 후속

- [x] 하위 라벨 접기/펼치기 — 폴더 패널의 라벨이 `부모/자식` 계층인데 접을 수 없다
  - Gmail 라벨의 `/` 구분을 계층으로 보고 부모 아래 자식을 들여써서 보인다. 부모 행에 ▸/▾ 토글을 두고 누르면 자식을 접고 편다(키보드: 화살표 좌우 또는 Enter/Space, `aria-expanded`, `role="tree"` 검토). 자식이 없는 라벨에는 토글이 없다
  - 접힘 상태는 계정별·라벨별로 `localStorage`에 저장해 다시 켜도 유지한다. 접힌 부모 줄에는 자식의 안 읽은 수 합계를 보여 줄지 정한다(제안: 합계 표시). 선택된 라벨이 접힌 부모의 자식이면 부모를 자동으로 펼친다
  - 테스트: 토글로 자식이 숨고 보임, 상태가 저장·복원됨, 자식이 선택돼 있으면 접히지 않음, 키보드 조작, 안 읽은 수 합계

## 화면 다듬기 (사용자 요청)

- [x] 다크 모드에서 HTML 메일 본문도 다크로 — 지금은 다크 모드에서도 본문이 흰 바탕이다
  - 원인(코드 확인): `tokens.css`의 `--mail-paper-bg/text/link`는 라이트 값만 있고 다크 값이 없으며, `mailHtml.ts`의 `buildMailDocument`가 iframe에 `color-scheme: light`와 이 값을 박아 넣는다. 2026-10-09 결정 로그("다크 모드에서도 본문은 밝은 바탕, 메일이 색을 직접 지정해 반전하면 가독성이 깨짐")를 **뒤집는 작업**이므로 `docs/decisions.md`에 새 결정을 적고 이전 줄에 "대체됨"을 표시한다
  - 어려운 점: HTML 메일은 인라인 스타일로 글자색·배경색을 직접 지정한다(검은 글자+흰 배경 전제, 흰 표·로고 이미지 등). 바탕만 어둡게 하면 검은 글자가 안 보이고, 전부 반전하면 이미지·브랜드 색이 깨진다. 방식을 비교해 정한다
    1. 글자색·배경색을 계산해 보정: 정제 단계(DOMPurify 훅)나 iframe 안에서 요소별 `color`·`background`를 읽어 밝기 대비가 낮으면 다크 팔레트로 바꾼다(배경이 밝은 요소는 어두운 바탕으로, 어두운 글자는 밝게). 지정이 없는 요소는 토큰 색을 상속
    2. CSS 필터 반전(`filter: invert(1) hue-rotate(180deg)`)+이미지·동영상·`[style*=background-image]`는 다시 반전해 원색 유지: 구현이 단순하고 대부분 읽히지만 색이 어긋날 수 있다
    3. 메일 자체가 다크를 지원하면(`prefers-color-scheme: dark` 미디어 쿼리가 있으면) 그대로 따르고, 없는 메일에만 1 또는 2를 적용
    - 제안: 3 → 1 순서로 적용하고, 반전이 어색한 메일을 위해 본문 위에 **"원본 보기"(밝은 배경으로 보기) 토글**을 둔다(선택은 메일마다가 아니라 전역 기억은 후속). 테스트용 샘플: 흰 배경 뉴스레터, 검은 글자만 있는 단순 메일, 표·로고 이미지가 있는 영수증, 인라인 스타일 없는 텍스트성 HTML
  - 토큰: 다크용 `--mail-paper-bg/text/link`(+ 인용선·표 테두리 색)를 `tokens.css`의 다크 블록에 추가하고, 하드코딩된 `#d4d4d8`(`blockquote`)도 토큰 값으로 넘긴다. `color-scheme`을 테마에 맞춰 `dark`로 바꾼다. 시스템 테마 따라가기에서 테마가 바뀌면 열려 있는 본문 iframe도 다시 그린다(`readPaperColors`를 테마 변경에 반응하게)
  - 본문 주변도 확인: 일반 텍스트 본문, 외부 이미지 차단 배너, 첨부 영역, 인용 블록, 검색어 강조(`<mark>`)가 다크에서 읽히는지. 깜빡임 방지: 다크에서 iframe 로드 전 흰 바탕이 번쩍이지 않게 iframe 바탕도 토큰으로
  - 테스트: 다크일 때 `buildMailDocument`가 다크 색·`color-scheme: dark`를 쓰고 라이트는 그대로, 인라인 검은 글자가 다크 바탕에서 대비 4.5:1 이상으로 보정됨(대비 계산 함수 테스트), 이미지 색은 유지, 테마 전환 시 다시 그림, "원본 보기" 토글
  - 완료 메모: `mailHtml.ts`가 다크일 때 iframe 문서를 `invert(1) hue-rotate(180deg)`로 반전하고 이미지·영상은 재반전. `tokens.css` 다크 블록에 `--mail-paper-*` 추가, 테마 전환 시 `HtmlBody`가 다시 그림. 이전 "항상 밝은 바탕" 결정은 decisions.md에서 뒤집음.

Gmail은 `X-GM-LABELS`(`STORE … +X-GM-LABELS (라벨)` / `-X-GM-LABELS`)로 붙이고 떼며, 라벨 생성은 IMAP `CREATE`(해당 이름의 메일함 생성 = 라벨 생성), 이름 변경은 `RENAME`, 삭제는 `DELETE`(라벨만 지워지고 메일은 남음)를 쓴다. 네이버는 라벨이 없으므로 "라벨" 대신 **폴더로 이동**(기존 `move_mail` 재사용)으로 대체하거나 메뉴에서 숨긴다 — 결정을 `docs/decisions.md`에 적는다. `MailProvider` trait에 `add_label`/`remove_label`/`create_label`/`rename_label`/`delete_label`을 추가하고 기본 구현은 `Unsupported`, `supports_labels()`로 UI가 분기하지 않게 command가 알려 준다(상위 계층에 서비스별 분기 금지)
  - **UI**: 메일 본문 툴바와 목록의 선택 상태에 "라벨" 버튼(단축키 `l`) → 팝오버: 라벨 검색 입력, 체크박스 목록(이미 붙은 라벨은 체크, 여러 메일을 고르면 일부만 붙은 라벨은 중간 상태), 맨 아래 "새 라벨 만들기"(입력한 이름으로 바로 생성하고 붙임, `부모/자식` 이름 허용). 시스템 폴더(받은편지함·보낸편지함 등)는 목록에서 제외. 본문 헤더의 라벨 칩에서 × 로 떼기. 폴더 패널의 라벨 행 우클릭/더보기에 "이름 바꾸기"·"삭제"(삭제는 확인 창: 메일은 지워지지 않음을 안내). 라벨 색은 기존 `labelColor` 함수를 쓴다. 문구는 한국어, 색·크기는 토큰만
  - 낙관적 갱신: 로컬 `messages.labels`를 먼저 바꾸고 서버 조작은 `pending_ops`에 쌓는다(오프라인이면 남음, 순서 보장). 실패하면 되돌리고 한국어 안내. 붙이기/떼기 뒤 폴더 패널의 라벨별 안 읽은 수·개수 갱신. 라벨 이름 변경·삭제 때는 로컬 `folders`·`messages.labels`의 이름도 함께 바꾼다(재동기화로 어긋나지 않게). 라벨 이름 검증: 빈 이름·예약 이름(`INBOX`, `[Gmail]/…`)·너무 긴 이름·금지 문자 거절
  - 되돌리기: 라벨 붙이기/떼기는 토스트에 "실행 취소"(기존 보관 취소 패턴 재사용)
  - 테스트: Rust — `FakeProvider`로 붙이기/떼기가 로컬과 큐에 반영됨, 여러 메일 일괄, 시스템 라벨 거절, 이름 검증, 이름 변경이 메일의 라벨에도 반영, 삭제해도 메일은 남음, 네이버형(미지원)은 `Unsupported`를 한국어 오류로, 오프라인 시 큐에 남음. UI — 팝오버 체크/해제가 `addLabel`/`removeLabel` 호출, 일부 붙음 중간 상태, 새 라벨 생성, 칩 ×, 이름 바꾸기·삭제 확인 창, `l` 단축키. 실서버(Gmail) 확인은 사용자가 요청할 때
